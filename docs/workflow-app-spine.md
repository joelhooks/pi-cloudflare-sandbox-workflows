# Workflow App Spine

Status: production-intended app spine
Code: `src/app/`
Integration contract: `pnpm test:integration`

This document describes the app spine for stochastic dynamic workflow planning, generated XState workflow machines, generated harnesses, deterministic safety-envelope execution, Artifact-backed packages, capability leasing, and Discord message delivery through a leased capability.

The app is deliberately not named after a launch phase. Configured familiar names are data supplied by packages, fixtures, or operator config. The core domain models actors, packages, dynamic plans, generated workflow machines, generated harnesses, plan artifacts, context capsules, safety-envelope states, agent lanes, capabilities, leases, receipts, and review gates.

## Architecture Summary

```txt
Worker/front door
    -> Cloudflare Worker route adapter
    -> WorkflowApp use case
    -> ContextCapsule port
    -> PackageRegistry port
    -> ArtifactStore port
    -> DynamicWorkflowPlanner port
    -> AgentPlanner/Worker/Verifier lane ports
    -> CapabilityLeaseBroker port
    -> DiscordMessage adapter
    -> WorkflowObservabilityRecorder port
    -> ReviewGate port
    -> HitlReportRenderer port
    -> ReviewSurfacePublisher port
```

Production code is split by boundary:

| Path                      | Boundary                       | Owns                                                                                              |
| ------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------- |
| `src/app/domain/`         | Domain contracts               | Zod schemas, inferred TypeScript types, canonical JSON hashing                                    |
| `src/app/application/`    | Application layer              | Use case orchestration and ports                                                                  |
| `src/app/workflow/`       | Workflow machines              | Deterministic supervisor envelope and generated-machine adapter                                   |
| `src/app/control-plane/`  | Control-plane adapter contract | D1 schema SQL and row validators                                                                  |
| `src/app/infrastructure/` | Adapters                       | Concrete adapters plus test-only memory adapters; future Cloudflare/Discord adapters plug in here |
| `src/app/worker.ts`       | Cloudflare Worker entrypoint   | Exported Worker handler, Sandbox class, and capsule Durable Object class                          |

Ports point inward. Adapters implement external behavior outward. The Vitest integration contract composes memory adapters, an integration-test dynamic planner adapter, integration-test worker lane receipts, and a dry-run Discord adapter. The application service depends only on ports.

`provisionCloudflareArtifactsRunStore` creates a per-run Cloudflare Artifacts repo and returns the Git-backed `ArtifactStoreContract`, remote, repo name, token secret, and expiry metadata. The store writes plan-phase files by committing/pushing to the repo default branch and reads lane outputs by `artifactCommitSha` when planner/verifier lanes push their own branch commits.

`createAdmittedAgentLaneRuntime` wraps any real `AgentLaneRuntimePort` with `AgentLaneAdmissionControllerContract` before planner, worker, or verifier lanes execute. It asks for an admitted slot with `runId`, `workItemId`, `laneId`, lane kind, requested time, and `maxActiveLanes`; it refuses deferred or already-completed lanes; it releases the slot as completed or failed with lane commit evidence when available. This makes bounded hot lanes a port contract, not caller discipline.

`CloudflareWorkflowCapsuleSupervisor` is the production-intended Durable Object adapter for the context capsule and lane admission contracts. `createCloudflareCapsuleSupervisorClient` resolves capsules by external `workItemId`, appends workflow events, admits bounded active lanes, records completed/failed lane releases, and exposes the same ports that `WorkflowApp` and the admitted runtime decorator consume.

`src/app/worker.ts` is the Cloudflare Worker entrypoint. `wrangler.jsonc` binds Cloudflare Artifacts, D1, the Sandbox container Durable Object, the workflow capsule Durable Object, non-secret policy vars, and required Worker secrets. `worker-configuration.d.ts` is generated by `pnpm exec wrangler types`; do not hand-write `Env`. `createWorkflowWorkerHandler` handles `POST /runs`, rejects wrong methods and invalid JSON/schema payloads before the app boundary, and delegates to the front-door contract.

The Worker also exposes package seed admin routes for control-plane setup. `POST /admin/packages/seed` is the one-shot route. The deploy harness uses the safer two-phase path: `POST /admin/packages/prepare-seed` creates/updates Cloudflare Artifacts repos and returns short-lived write tokens, the local deploy process pushes `package.json`, then `POST /admin/packages/finalize-seed` mirrors package plus entitlement rows into D1. The routes are guarded by `WORKFLOW_APP_ADMIN_TOKEN`. This is setup for package discovery/pinning; it is not a workflow side-effect capability.

`createCloudflareWorkflowFrontDoor` is the production-intended composition root for `POST /runs`. It provisions a per-run Cloudflare Artifacts repo, resolves the Durable Object capsule/admission client, issues redacted `AgentAuthLease` metadata for the Pi auth secret ref, wraps the Cloudflare Sandbox Pi runtime with admission, wires real planner/worker/verifier lane adapters, wires the plan-selected deterministic verifier adapter, wires the D1 + Artifacts package registry, constructs the run-scoped D1 + Artifacts capability lease broker when no test broker is injected, and constructs `WorkflowApp` in production mode.

`createCloudflareCapabilityLeaseBroker` is the production-intended Cloudflare capability broker for `discord.message.send`, `wzrrd.site.publish`, `github.branch.commit`, and `github.pull-request.create`. D1 stores the queryable lease and receipt status rows; Artifacts stores redacted lease and execution receipts. Denied requests do not mutate D1, which keeps failed policy probes from looking like issued authority.

`createCloudflareDiscordMessageAdapter` is the production-intended Discord execution adapter. It accepts only a leased `discord.message.send` operation, double-checks payload hash, resource binding, review approval, and trusted secret ref before real sends, resolves the bot token only inside the adapter, calls Discord API v10 `POST /channels/{channel_id}/messages`, disables ambient mentions with `allowed_mentions.parse: []`, uses `nonce`/`enforce_nonce` for idempotency, and returns redacted delivery results. Dry-run returns a leased dry-run delivery without materializing the bot token or calling Discord. `WorkflowApp` writes a typed `workflow.discord-message-approval.v1` artifact for actors with `discord.send`, then uses that artifact as the approved review gate for real `discord.message.send` leases.

## Domain Model

### Dynamic Workflow Blueprint

A `PlanProposal` is stochastic operator/agent intent. It is not executable truth.

A `DynamicWorkflowBlueprint` is the planner output before artifact pinning. It contains:

- a `DynamicWorkflowMachineDocument`
- a `DynamicWorkflowPlanBase`
- a generated harness document
- a verification contract document
- planner lane prompt/transcript evidence
- output target and side-effect declarations

For a real Pi planner lane, the strict agent output is `PlannerLaneBlueprintDocument`: `machine`, `harness`, `plan`, and `verificationContract` only. The planner does **not** author its own lane evidence. `createCloudflarePiPlannerLaneAdapter` runs the real lane through `AgentLaneRuntimePort`, reads the structured blueprint artifact from Artifacts, reads the transcript artifact, validates the blueprint, and then attaches the real prompt/transcript/output receipt as `plannerLane` evidence.

Real lane receipts include `artifactCommitSha` so the app can read the exact planner/worker/verifier output commit rather than whatever the repo default branch currently points at. Verifier lanes receive explicit output evidence snapshots loaded from worker lane commits, because worker output branches are not automatically local in the verifier sandbox. Real `pi-*` lane receipts also include `authLease`, a redacted `AgentAuthLease` that records the lease id, secret ref, scope, run/work item, issued timestamp, and expiry timestamp. The leased material is handed only to the sandbox runtime; prompts, plans, Artifacts, review surfaces, and receipts carry metadata. Deployed Cloudflare Sandbox receipts now include `sandboxAccounting` with command duration and a destroyed-cleanup receipt emitted after sandbox teardown.

The planner can be stochastic. The app pins the generated XState machine config, optional generated machine TypeScript source for inspection, generated harness/source only when new bindings are needed, verification contract, and planner lane evidence first, then writes `run/plan.json` with those artifact refs and hashes.

### Generated XState Workflow Machine

The generated XState machine owns run-specific workflow order.

The app pins the executable machine artifact before execution:

- `workflows/machine.config.json`: validated `workflow.xstate-machine.v1` config

Execution loads the config ref, checks its hash, validates the machine against plan step ids, starts an XState actor from the validated config in the trusted runtime, reads each state's `meta.stepId`, executes the bound step, and sends `STEP_DONE` or `STEP_BLOCKED` back into that actor.

Generated TypeScript source may be emitted as an inspectable/debuggable artifact, but it is not required for execution and should not be treated as arbitrary code to run inside the control plane.

The fixed app machine is only the supervisor/safety envelope. It is not the workflow shape.

### Dynamic Workflow Plan

A `DynamicWorkflowPlanDocument` is the pinned execution contract that binds run data to the generated machine.

The plan document contains:

- `schemaVersion: "workflow.dynamic-plan.v1"`
- `planner.kind: "stochastic"`
- planner nonce/source metadata
- generated machine artifact refs and hashes
- generated harness artifact ref and hash, only when the planner creates new step bindings or adapter wiring
- verification contract artifact ref and hash
- planner lane prompt/transcript/receipt refs
- selected `PinnedPackage` refs
- dynamic step data keyed by step id
- side-effect payload refs and hashes
- output target
- review gates and secret refs for leased capabilities
- safety flags requiring capability leases and scratch-only compute

Current step kinds:

- `research.review`
- `capability.discord.message`
- `review.summary`

### Safety Envelope

The fixed app XState machine is the deterministic safety envelope. It is not the workflow shape.

The generated XState machine owns the run-specific workflow. The safety envelope enforces:

- capsule resolution
- package metadata discovery
- entitlement/pinning checks
- generated XState machine and dynamic plan generation
- generated XState machine pinning and hash verification
- generated harness and verification contract pinning and hash verification
- plan pinning and hash verification
- capability lease boundaries
- adapter execution boundaries
- receipt recording
- review summary capture
- blocked/captured terminal states

### Package

A package is the top-level saved primitive. It is a repo-backed module rooted at `package.json`. The manifest is the source of truth for metadata, exports, dependencies, apps, services, jobs, workflows, subscriptions, retrievers, adapters, checks, publish artifacts, and runtime surface.

Context packs, workflow packs, tool packs, support packs, adapters, org kernels, and personal kernels are package categories. Agents discover package metadata first, not the whole content blob. Full mount or invocation happens only after entitlement, version pinning, manifest/hash verification, and trust policy.

D1 can index package metadata and entitlements. D1 is not the package.

The app separates:

- `PackageMetadata`: discoverable/indexed metadata from `package.json`.
- `PinnedPackage`: immutable Artifact ref selected for a run, with manifest hash, file hashes, version, and pinned timestamp.

`createCloudflareD1PackageRegistryActor` implements `PackageRegistryActorContract` for the production-intended Cloudflare control plane. It uses D1 `packages` and `package_entitlements` rows only as an index/authorization surface, then reads the package manifest from Artifacts before returning metadata or pinning a package. The adapter verifies the manifest against the D1 row and optional manifest hash; stale or mismatched rows block pinning with `stale_package`.

For deployed Cloudflare package reads, D1 `packages.artifact_ref` should point at a concrete package manifest location:

```txt
artifact://cloudflare-artifacts/<repo-name>/package.json
```

The manifest can still carry logical package refs and exported contracts. The Cloudflare reader only resolves the physical Artifacts repo/path.

Seed the default package substrate through the deploy harness after the Worker has D1, Artifacts, and admin token bindings:

```bash
pnpm app:deploy
```

The one-shot admin route remains available for controlled setup:

```bash
curl -X POST "$WORKER_URL/admin/packages/seed" \
  -H "Authorization: Bearer $WORKFLOW_APP_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"subjects":[{"subjectType":"actor","subjectId":"actor:operator"}]}'
```

Static package imports are pinned/bundled snapshots. Dynamic package invocation resolves the current published package export at runtime and must be checked before execution. Package-to-package calls need idempotency keys and depth limits so workflow dispatch does not duplicate work or loop forever.

### HITL Report Node

A HITL report node is an installable workflow-node package export that renders typed workflow artifacts into a human review surface.

It is package infrastructure, not a side-effect adapter. It must be discovered, entitled, pinned, hash-checked, and invoked like any other package export. External delivery is separate and goes through a capability lease such as `wzrrd.site.publish`.

Seed package shape:

```txt
@joelhooks/wzrrd-hitl-report
  export renderReviewSurface
  template joel/tufte-mdsvx
```

The report node input should include run id, review kind, pinned artifact refs, redaction policy, operator-facing title, and intended output target. The output should include a build artifact ref, surface hash, redacted summary ref, and a machine-readable review contract. A dynamic workflow can install/use the node after synthesis or verification and before delivery:

```txt
synthesizeResults
  -> renderHitlReport
  -> requestReviewSurfaceDeliveryLease
  -> executeReviewSurfaceDelivery
  -> waitForHumanDecision
  -> route accept/edit/reject/needs_more_evidence
```

This keeps the Wzrrd/Tufte report template available as a plugin-like workflow node for Dreaming, support sweeps, capability approvals, implementation reviews, and other HITL gates without hardcoding a report style into the safety envelope.

HITL report nodes should render the workflow state machine as a first-class figure. Preferred source order: pinned generated XState machine artifact, then pinned workflow-plan artifact, then an explicitly labeled fallback diagram. The report must show the proof level. If the run only proves dynamic evidence-driven lane assembly over a static pattern library, say that; do not label it as a generated XState workflow machine. D2 is the current figure format because it gives agent-readable source and reproducible SVG output for Wzrrd review surfaces.

### Agent Lane

An agent lane is a planner, worker, or verifier execution lane with runtime evidence. Pi is the first production runtime target, but the domain does not hardcode Pi as the lane concept. Valid runtime families include `pi-agent-cli`, `pi-agent-rpc`, `pi-sdk-runPrintMode`, future `think-framework`, and `integration-test`.

`integration-test` receipts must carry `realAgent: false` and are accepted only when `WorkflowApp` is constructed in integration-test mode. Real Pi or Think runtime receipts must carry `realAgent: true`. This keeps the test harness useful without pretending local memory execution is real agent work.

Real Pi lane receipts must also carry redacted auth lease metadata. The domain schema rejects production-mode `pi-*` receipts that omit `authLease`, which keeps the lease boundary visible in the review surface instead of hiding it in adapter config.

Lane admission is a separate domain contract:

- `AgentLaneAdmissionRequestSchema`
- `AgentLaneAdmissionDecisionSchema`
- `AgentLaneReleaseRequestSchema`
- `AgentLaneReleaseReceiptSchema`

Admission decisions are `admitted`, `deferred`, or `already-completed`. Release receipts record the lane kind/id, run/work item, release status, active lane set after release, and optional Artifacts commit SHA. The app can schedule many planned lanes, but only admitted lanes are hot Cloudflare Sandboxes.

### Context Capsule

A context capsule is the durable actor keyed by work item/thread. It records run state, events, pinned package refs, and review state. Sandboxes/containers are scratch compute and do not own durable state.

### Capability Lease

A capability lease is permission to perform one exact operation:

- actor and role context
- capability name
- resource
- payload ref and payload hash
- expiry
- review gate
- secret ref
- receipt sink
- run/work item ids

Dry-run still uses the lease path. Dry-run only relaxes review/secret material requirements.

## Capability Lease Schema

The domain lease contract is Zod-first. TypeScript types are inferred from the schemas.

Core schemas:

- `CapabilityLeaseRequestSchema`
- `CapabilityLeaseSchema`
- `CapabilityLeaseDecisionSchema`

Current capabilities are:

```txt

github.branch.commit
github.pull-request.create
linear.comment.create

```

The Discord resource shape is:

```json
{
  "kind": "discord.channel",
  "serverRef": "discord:server:...",
  "channelRef": "discord:channel:..."
}
```

The lease binds the exact message body by SHA-256 hash. The generated machine routes to the capability step; the dynamic plan references the payload artifact and carries the review gate and secret ref. The receipt records the channel/server refs, payload hash, dry-run/send outcome, review gate, policy id, lease id, secret ref, and redacted receipt ref.

The Wzrrd resource shape is:

```json
{
  "kind": "wzrrd.site",
  "siteRef": "wzrrd:...",
  "slug": "run-or-review-slug"
}
```

The Wzrrd lease binds a typed `wzrrd.publish-payload.v1` artifact by canonical JSON hash. The payload points at the already-captured `workflow.review-surface.v1` artifact, its hash, surface id, run id, work item id, title, and slug. Dry-run delivery records the intended URL and receipt without public publication. Real publication requires the configured Wzrrd publish secret ref, a `workflow.wzrrd-publish-approval.v1` approval artifact, an approved review gate, and adapter-side review-surface hash verification before the Wzrrd API call.

## Discord Capability Policy

Policy for `discord.message.send`:

- The generated XState machine must route to a dynamic plan step that requests a capability lease.
- The resource must bind server and channel refs.
- The payload must be stored as a pinned payload artifact.
- The payload hash must equal the message body hash.
- Dry-run execution is allowed without human approval.
- Real send requires a review approval ref and reviewer actor id.
- Real send requires a trusted Discord secret ref.
- The sandbox/agent never sees a raw Discord token.
- The receipt must be redacted and must not include token material.

The integration contract uses `createDryRunDiscordMessageAdapter`. It refuses non-dry-run leases with `adapter_unavailable`; it does not fake a real send.

The production-intended broker is `createCloudflareCapabilityLeaseBroker`. It validates actor identity, capability name, review mode, trusted secret ref for real sends, and pinned payload hash before issuing a lease. It writes issued leases and Discord execution receipts as redacted Artifacts records, mirrors their queryable status in D1, and records denial decisions without persisting lease rows.

The production-intended execution adapter is `createCloudflareDiscordMessageAdapter`. It follows Discord's current API v10 message-send shape: bot-token authorization, `POST /channels/{channel_id}/messages`, JSON content, and explicit `allowed_mentions` suppression. It blocks unapproved sends, secret-ref mismatches, resource mismatches, payload hash drift, Discord auth failures, and rate-limit failures as redacted `DiscordDeliveryResult` blockers.
